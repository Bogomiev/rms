# Файлы и каталоги

Миграция `006_files.sql` выполняется при запуске. Идентификаторы — UUID,
`icon` хранится как BYTEA и передается в JSON как base64. `parent_id: null`
означает корень. Уникальность имени внутри каталога учитывает удаленные записи.
Для повторного использования имени нужно окончательно удалить старую запись.

## Конфигурация

```yaml
s3_path: https://s3.regru.cloud/
s3_bucket: YOUR_BUCKET
s3_region: us-east-1
s3_access_key: ""
s3_secret_key: ""
```

Можно использовать `RMS_S3_PATH`, `RMS_S3_BUCKET`, `RMS_S3_REGION`,
`RMS_S3_ACCESS_KEY`, `RMS_S3_SECRET_KEY`. Секреты задаются в окружении либо в
игнорируемом Git файле `config/local.yaml`. Бакет должен уже существовать.
Без `s3_bucket` S3 отключен: чтение метаданных и мягкое удаление доступны,
запись объектов и окончательное удаление возвращают 503.
S3 credentials должны разрешать HeadObject/GetObject, PutObject,
ListBucket для префикса `files/` и DeleteObject.

## API

Все маршруты используют существующую cookie-авторизацию. Изменяющие запросы
также требуют существующий CSRF-заголовок (`X-CSRF-Token`).

| Метод | URL | Назначение |
|---|---|---|
| GET | `/files/` | Корневые записи, сортировка priority, name, id |
| GET | `/files/?parent_id=UUID&include_deleted=true` | Дочерние записи, включая помеченные |
| GET | `/files/UUID` | Метаданные по ID, включая помеченные |
| GET | `/files/by-path?path=/docs/report.txt` | Метаданные по логическому пути, только активные |
| POST | `/files/` | Создание с UUID клиента |
| PUT | `/files/UUID` | Полная замена изменяемых метаданных и необязательная замена содержимого |
| DELETE | `/files/UUID` | Мягкое удаление (marked=true по умолчанию) |
| DELETE | `/files/UUID?marked=false` | Окончательное удаление S3-объектов и записи |

Пример тела POST (PUT имеет такую же структуру, `id` можно опустить):

```json
{
  "id": "a7954397-4aee-48e1-8b90-d5bbca8bf5f3",
  "name": "report.txt",
  "priority": 10,
  "parent_id": null,
  "is_file": true,
  "icon": null,
  "content": "aGVsbG8="
}
```

`content` и `icon` — base64. Для пустого файла передайте `content: ""`.
Для каталога задайте `is_file: false` и опустите `content`.
При PUT отсутствие/null content сохраняет текущее содержимое; остальные поля
передаются целиком. Тип `is_file` менять нельзя. Если объект пропал из S3,
для обновления файла нужно снова передать содержимое.
Размер JSON ограничен 48 MiB (практический предел файла около 36 MiB без иконки).
Для больших загрузок может понадобиться увеличить HTTP timeout в конфигурации.
GET возвращает метаданные, без скачивания содержимого.

Ответы: POST 201, GET/PUT 200, DELETE 204; ошибки входных данных 400,
отсутствие записи 404, конфликт имени/типа/дерева 409, S3 отключен 503.
Непустые каталоги нельзя ни пометить, ни удалить. Сначала удалите дочерние записи,
включая помеченные. Восстановление помеченных записей этим API не предусмотрено.

## Согласованность и повторы

PostgreSQL-транзакция с advisory lock сериализует операции сервиса между
экземплярами приложения. Сначала S3, затем SQL и commit. Объекты содержимого
неизменяемые: `files/UUID/SHA256`. Каталоги представлены пустым маркером
`files/UUID/`; логическая иерархия хранится в БД, а переименование/перенос
не требует копирования S3-префиксов.

Клиент генерирует UUID до POST и повторяет тот же UUID и тело при сбое. SDK
проверяет существование объекта через HEAD и повторно не загружает его.
Повтор POST с несовместимыми метаданными или содержимым дает 409.
После сбоя БД при PUT старый ключ и содержимое остаются рабочими; повтор PUT
использует уже загруженную новую ревизию. Старые ревизии и объекты после
неповторенных неудачных записей остаются в S3. Окончательное удаление удаляет
все ревизии UUID. Объекты без записи после брошенного POST требуют отдельной
периодической сверки/очистки; автоматического сборщика пока нет.

Распределенной ACID-транзакции между S3 и PostgreSQL нет. Если commit после
окончательного удаления S3 не удался, запись может временно указывать на
отсутствующий объект: повтор DELETE завершает удаление записи. Отсутствие
объектов в S3 не мешает окончательному удалению. При включенном versioning
S3 DeleteObject оставляет версии по правилам бакета; для очистки старых версий
нужна lifecycle policy бакета.
