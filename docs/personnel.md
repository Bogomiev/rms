# Пользователи, должности и роли

Все ответы используют стандартный формат RMS: `resultCode`, необязательный `messages` и `data` (для ответов с данными).
Чтение доступно авторизованным пользователям; POST, PUT и DELETE — администраторам с обычной проверкой CSRF.

| Ресурс | Список | Одна запись | Добавление | Сохранение | Удаление |
| --- | --- | --- | --- | --- | --- |
| Пользователи | GET /users | GET /users/{id} | POST /users | PUT /users/{id} | DELETE /users/{id} |
| Должности | GET /positions | GET /positions/{id} | POST /positions | PUT /positions/{id} | DELETE /positions/{id} |
| Роли | GET /roles | GET /roles/{id} | POST /roles | PUT /roles/{id} | DELETE /roles/{id} |

Списки поддерживают `limit` (1–100, по умолчанию 50) и `offset` (по умолчанию 0).

Тело POST/PUT роли: `{"name":"orders"}`. Допустимы только `admin`, `orders`, `products`, `documents`, `goods-receipts`, `goods-distribution` (точное совпадение). Другие имена возвращают 400; повторное имя при создании или переименовании — 409. Уникальность обеспечена ограничением БД, включая параллельные запросы.

Тело POST/PUT должности: `{"name":"Кассир","role_ids":[1,2]}`.
PUT полностью заменяет список ролей в одной транзакции; пустой или отсутствующий `role_ids` снимает все назначения. Одна роль может принадлежать нескольким должностям.

Тело POST/PUT пользователя:

```json
{"name":"Иван","user_token":"ivan","password":"password","is_admin":false,"position":1,"login_blocked_until":null}
```

При PUT пустой или отсутствующий пароль сохраняет прежний хеш. `position: null` снимает должность; отсутствие поля при PUT также снимает её. POST требует пароль. Пароль и его хеш в ответах отсутствуют.

В списке пользователей и карточке (в `data`), а также при логине, обновлении и восстановлении сессии (в `data.user`) возвращаются поля `position` (идентификатор или null) и `position_name` (название или null). Остальные поля пользователя: `id`, `user_token`, `name`, `isAdmin`, `login_blocked_until` (RFC3339 или null). GET /users/{id}, login, refresh и session дополнительно возвращают `roles: [{"id":1,"name":"Продажа"}]`; без назначенных ролей — `[]`.

Успешное добавление возвращает HTTP 201, чтение/изменение/удаление — 200. Некорректные данные — 400, отсутствующий объект — 404, дубликат названия/токена или нарушение внешнего ключа — 409.

Миграция 007 применяется при запуске. Создаёт роли `admin`, `order`, `product`, `document`, `goods-receipts`, `goods-distribution` и должности `admin`, `seller`. Пользователь с `user_token = admin` получает должность admin и флаг администратора, остальные — seller без флага. У admin только роль admin, у seller остальные пять ролей. Новая пустая база создаёт первого администратора с должностью admin. Названия справочников уникальны и не могут быть пустыми. Повторная пара должность–роль запрещена. Удаление роли или должности блокируется, если на неё ссылаются другие таблицы, включая таблицу соответствий; сначала нужно снять назначения. Удаление пользователя блокируется при наличии сессий, включая отозванные сессии, пока они не удалены. Эффективный административный доступ определяется флагом `is_admin`, ролью admin, отсутствием должности или отсутствием ролей у должности.


При записи пользователя `is_admin=true` устанавливает должность admin; выбор должности admin устанавливает флаг. При сохранении должности наличие роли admin исключает остальные роли. Поле `login_blocked_until` можно установить или очистить через POST/PUT пользователя.

Пароль задаётся в общей операции сохранения: браузер держит его только в памяти карточки, отправляет JSON через существующий защищённый POST/PUT, RMS хеширует bcrypt. Отдельного метода для этого не требуется. Новый пароль не попадает в localStorage и ответы API. До сохранения карточки пароль в базе не меняется.

При обновлении сессии права перечитываются из базы. Проверка действующей сессии также учитывает актуальный admin и блокировку; изменение эффективных прав не ждёт истечения JWT.

Соответствие ecom_orders: order → интернет-заказы; product → информация о товаре; goods-receipts → приёмка; document → документы в сервис-деске; goods-distribution → сервис выдачи (самостоятельного сервиса выдачи сейчас нет). Администратор видит все сервисы. Блоки верхнего уровня и вложенные сервисы проверяются каждый по собственному соответствию сервис–роль. Права родителя не выводятся из ролей дочерних сервисов. Отсутствие соответствия означает безусловное отображение, в том числе для новых сервисов. Общая панель «Товары», «Подсчёт товара», «Сервис-деск», «Задания», «Контакты» и «Дашборд» не имеют собственных ролей и отображаются безусловно. Вложенные документы по-прежнему требуют document. Пользователь без должности или с должностью без ролей получает поведение администратора во всех сервисах и проверках RMS. Значение `role` в ответах авторизации отражает эффективный доступ; поле `isAdmin` пользователя сохраняет значение из базы. Это ограничение отображения; оно не добавляет проверки бизнес-ролей к API операций с заказами и товарами.

Если 007 уже применена в конкретной базе, изменённый файл автоматически повторно не выполняется: стартовый загрузчик отслеживает имя миграции. Для такой базы необходимо отдельно применить наполнение либо оформить следующую миграцию.

### Выбор магазина

Должности возвращают и принимают `store_selection_available` («Доступен выбор
магазина») и `store_selection_required` («Выбор магазина обязателен»).
Эти же поля возвращаются в данных пользователя, при входе и обновлении сессии.
В ecom_orders они сохраняются вместе с должностью в `ecom-orders-user`.

В ecom_orders список `STORE_DEPENDENT_SERVICES` в `shared/lib/permissions.ts`
содержит заказы и приемку: без выбранного магазина они скрыты.

Признак должности `seller_selection_available` («Доступен выбор продавца») принимается методами создания и изменения должностей и возвращается в должностях, пользователях, данных сессии и `/usertokenvalid`. По умолчанию выключен; ecom_orders показывает меню продавца только при значении `true`.
