# RMS

HTTP API личного кабинета сотрудников магазина. Go 1.27.1, PostgreSQL; слои HTTP → сервисы → хранилище.

Для запуска создайте отдельную пустую БД `rms`, скопируйте `config/example.yaml` в `config/local.yaml` и задайте параметры подключения. Миграции применяются автоматически. Для существующей БД с начальной схемой RMS миграция 002 добавляет счётчик неверных PIN и время блокировки без удаления данных.

```bash
export CONFIG_PATH=./config/local.yaml
export RMS_SIGNING_KEY="$(openssl rand -hex 32)"
go run ./cmd/rms-server
```

Сохраните `RMS_SIGNING_KEY` в окружении сервера между перезапусками: это ключ подписи JWT. При инициализации БД сервер проверяет наличие любых пользователей. Если таблица пуста, создаётся пользователь с именем и `user_token` равными `admin`, `is_admin=true`, паролем из `first_admin_pwd` в конфигурации. Пароль должен содержать 8–72 байта и хранится в БД только в виде bcrypt-хеша. Если есть хотя бы один пользователь, новые учётные записи автоматически не создаются, пароли и права не изменяются. Проверка и создание выполняются в транзакции с блокировкой таблицы. При пустой таблице и незаданном или неверном пароле запуск завершается ошибкой. Сервер слушает `localhost:8082`; для браузера разместите его за HTTPS reverse proxy на одном сайте с фронтендом.

## Запуск на проде через Makefile

Makefile в корне репозитория оборачивает Docker Compose и делает управление сервером на проде однокомандным: полный список команд — `make help`, то же самое в виде интерактивного меню — `make menu`.

Первый запуск на новом сервере:

```bash
git clone https://github.com/Bogomiev/rms.git
cd rms
make install
```

`make install` проверяет наличие Docker и Docker Compose (предложит установить при необходимости), спрашивает про PostgreSQL (свой контейнер или внешний сервер), создаёт `config/local.yaml` и `.env`, генерирует пароль первого администратора и `RMS_SIGNING_KEY`, затем собирает и запускает контейнеры.

Дальнейшее управление:

| Команда | Что делает |
| --- | --- |
| `make status` / `make logs` | Статус контейнеров и healthcheck / логи (Ctrl+C для выхода) |
| `make deploy` | `git pull` текущей ветки деплоя, пересборка образа RMS и перезапуск контейнера |
| `make autodeploy` / `make autodeploy-off` | Включить/выключить cron-задание, которое раз в час само выполняет `make deploy` |
| `make branch` | Показать текущую ветку деплоя и её статус относительно GitHub (отставание/опережение, незакоммиченные изменения, включён ли автодеплой) |
| `make branch-master` / `make branch-dev` | Переключить ветку, которую деплоит этот сервер (обычно прод следит за `master`, тестовый сервер — за `dev`) |

Кодовая база одна на оба сервера: скрипт `scripts/deploy.sh`, который запускается вручную (`make deploy`) и из cron (`make autodeploy`), сам определяет, на какой git-ветке сейчас находится локальный checkout, и подтягивает изменения именно из неё. Поэтому выбор окружения делается один раз командой `make branch-master` или `make branch-dev` на самом сервере — дальше `make autodeploy` следит уже за выбранной веткой без дополнительной настройки. При переключении ветки скрипт `make branch-*` спросит, пересобрать и перезапустить контейнер немедленно или дождаться ближайшего часового прогона автодеплоя.

| Метод | Назначение |
| --- | --- |
| `POST /auth/login` | JSON `{"user_token":"…","password":"…"}`; требует Origin; возвращает пользователя, идентификатор сессии и csrfToken, устанавливает cookies |
| `POST /auth/refresh` | Требует Origin и cookie `refresh_token`, атомарно заменяет сессию и обе cookies, возвращает новый csrfToken; access-токен не требуется |
| `POST /auth/logout` | Требует access-cookie, X-CSRF-Token и refresh-cookie; удаляет сессию и обе cookies |
| `GET /auth/session` | Проверяет access-cookie и активность сессии; возвращает csrfToken и userToken без ротации |
| `GET /usertokenvalid?token=…` | Без авторизации: 200, если пользователь с таким `user_token` существует; 400 для отсутствующего, пустого или неизвестного значения; 500 при ошибке БД |
| `GET /products` | С access-cookie: массив товаров в формате фронтенда |
| `GET /stores` | С access-cookie: список магазинов с метаданными пагинации |
| `GET /users/?limit=50&offset=0` | С access-cookie: список пользователей, лимит 1–100 |
| `POST /users/` | Только администратор: JSON `user_token`, `name`, `password`, `is_admin` |

`user_token` — уникальная непустая строка до 255 байт, идентификатор для входа вместе с паролем. В Go используется `UserToken`, в SQL и JSON — `user_token`. Сессии связаны с пользователем через `user_id`.

Access-cookie: `access_token`, HttpOnly, Secure, SameSite=Lax, срок 15 минут. Refresh-cookie: `refresh_token`, HttpOnly, Secure, SameSite=Strict, срок 2160 часов (90 дней, принято за 3 месяца). Обе имеют Path=/, Expires и Max-Age, без Domain. Сроки задаются `token_TTL` и `refresh_token_TTL`. JWT различаются по назначению. Токены не возвращаются в JSON и не принимаются из Authorization или тела запроса. Браузер отправляет cookies автоматически; для fetch при необходимости используйте `credentials: "include"`.

Пример ответа `/products`:

```json
[{"uid":"00000000-0000-0000-0000-000000000001","parent_id":"00000000-0000-0000-0000-000000000000","marked":false,"code":"001","name":"Товар","markingType":"none","isWeight":false,"isThermalMode":false,"barcodes":[{"barcode":"4600000000001","unit":"шт","ratio":1,"isBase":true}]}]
```

Пример ответа `/stores`:

```json
{"page":1,"perPage":1,"totalPages":1,"totalItems":1,"items":[{"id":"00000000-0000-0000-0000-000000000002","code":"001","name":"Магазин","uid_1c":"00000000-0000-0000-0000-000000000002","address":"Адрес"}]}
```

Список магазинов возвращается целиком одной страницей. Для пустого списка: `page=1`, остальные счётчики равны 0, `items=[]`. Пустой список товаров — `[]`. API сохраняет `uid` товара и `uid_1c` магазина как представления первичного ключа `id`. Товар дополнительно возвращает `marked` и `parent_id`. Клиентские `/api/rms/stores` и `/api/rms/products` доступны для запросов к RMS; существующие бизнес-запросы клиента к 1С сохранены.

Сервисы `product` и `store` предоставляют получение списка, получение по идентификатору, добавление, изменение и удаление (`Products`/`Stores`, `GetProduct`/`GetStore`, `AddProduct`/`AddStore`, `UpdateProduct`/`UpdateStore`, `DeleteProduct`/`DeleteStore`). HTTP-маршруты записи справочников пока не предусмотрены. SQL использует snake_case; вложенные штрихкоды сохраняются в JSONB.

Проверки:

```bash
go test ./...
go vet ./...
TEST_POSTGRES_DSN='host=localhost port=5432 user=rms dbname=rms_test sslmode=disable' go test ./internal/storage/postgres
```

Интеграционные тесты создают и удаляют собственные временные схемы; без `TEST_POSTGRES_DSN` они пропускаются.

Первичные ключи товаров и магазинов, а также `Product.ParentID`, имеют тип `uuid.UUID` в Go и `UUID` в PostgreSQL. `Product.ID` сериализуется в `uid`. В сущности магазина и его таблице отдельного идентификатора для 1С нет: HTTP-слой формирует `uid_1c` из `ID`.

Для товара действуют ограничения `code VARCHAR(11)` и `name VARCHAR(100)`, для адреса магазина — `VARCHAR(250)`. Строковые поля в Go имеют тип `string`; сервисы проверяют длину в символах. `parent_id` обязателен; для корня можно передать нулевой UUID. Внешний ключ на родителя не задан, чтобы порядок загрузки справочника не ограничивал импорт. Поля `created_at` и `updated_at` — `TIMESTAMP` в БД и `time.Time` в Go; они не включены в ответы списков. Методы PostgreSQL устанавливают их через `NOW()` и возвращают сохранённые значения через `RETURNING`; обновление не меняет дату создания.

Миграция `002_login_attempts.sql` добавляется к существующей начальной схеме RMS и выполняется автоматически один раз. Удалять БД при этом обновлении не нужно.

Планировщик находится в `internal/scheduler` и использует `github.com/robfig/cron/v3`. Пример настройки:

```yaml
scheduler:
  timezone: Asia/Vladivostok
  jobs:
    session_cleanup:
      enabled: true
      schedule: "@every 1m"
      timeout: 10s
```

Поддерживаются стандартные cron-выражения из пяти полей (`"0 3 * * *"` — ежедневно в 03:00 выбранного часового пояса) и дескрипторы `@every`, `@daily` и т.д. Отсчёт регулярных заданий начинается после запуска планировщика; немедленного выполнения очистки при старте нет. Очистка удаляет до 1000 истёкших сессий за запуск.

Для новой задачи реализуйте `func(context.Context) error`, добавьте её в реестр при вызове `scheduler.New` в `internal/app/app.go` и настройте имя в YAML. Неизвестные включённые задачи, неверные расписания и неположительные таймауты отклоняются при создании планировщика. Задачи получают контекст с таймаутом и должны учитывать его отмену. Паника перехватывается и логируется; параллельные запуски одной задачи в одном процессе пропускаются. При остановке сервер отменяет контексты задач и ждёт их завершения перед закрытием БД. При нескольких экземплярах RMS планировщик запускается в каждом; распределённой блокировки нет.

При первом запуске с новой пустой БД:

```bash
cd /home/tz/projects/go/rms
go mod tidy
go mod download
export CONFIG_PATH=./config/local.yaml
# signing_key уже настроен в local.yaml; альтернативно задайте RMS_SIGNING_KEY.
go run ./cmd/rms-server
```

Для обновления библиотек до актуальных совместимых версий используйте `go get -u ./...`, затем `go mod tidy`. Для пустой БД задайте `first_admin_pwd` в `config/local.yaml`; администратор `admin` создастся автоматически при запуске. Команда `rms-init` остаётся доступна для явного добавления администратора с другим `user_token` через параметры CLI и `RMS_ADMIN_PASSWORD`.

## Защита входа и CSRF

`app_origins` — список разрешённых origin приложений, без завершающего `/`, например `["https://orders.example.com", "https://admin.example.com"]`. Через окружение: `RMS_APP_ORIGINS=https://orders.example.com,https://admin.example.com` (без пробелов). Список имеет приоритет над устаревшим `app_origin` / `RMS_APP_ORIGIN`, который поддерживается для совместимости. Пустой список без legacy-настройки запрещён. В production обязателен HTTPS. Установите тот же origin в клиентском `APP_ORIGIN` и одинаковый постоянный `RMS_SIGNING_KEY` на обоих серверах (только серверное окружение). Без корректного Origin login/refresh отвечают 403, даже если запрос поступает напрямую в RMS. Не формируйте разрешённый origin из Host/X-Forwarded-Host запроса.

RMS создаёт отдельный случайный UUID `csrfToken` внутри access JWT при login/refresh и возвращает его на верхнем уровне JSON. Access JWT содержит `sid` — идентификатор сессии. Все защищённые запросы дополнительно проверяют сессию в БД: отзыв действует сразу, без ожидания истечения access JWT. Старый access JWT без `sid` требует refresh. Ротация refresh одноразовая и транзакционная: ошибка сохранения замены не удаляет старую сессию, конкурентный повтор не создаёт дополнительные сессии.

POST/PUT/PATCH/DELETE с access-cookie требуют совпадающий `X-CSRF-Token`; сравнение выполняется за постоянное время. Исключения — login и refresh, где используется Origin, поскольку access ещё отсутствует или уже истёк. `GET /auth/session` позволяет восстановить клиентский CSRF после перезагрузки. JWT не выдаются в JSON/localStorage; браузер сохраняет их через Set-Cookie. Пример login/refresh: `{"resultCode":0,"csrfToken":"uuid","data":{"sessionId":"…"}}` (login также включает `data.user`).

`max_login_attempts` / `RMS_MAX_LOGIN_ATTEMPTS` (по умолчанию 5) и `login_block_duration` / `RMS_LOGIN_BLOCK_DURATION` (по умолчанию 15m) управляют блокировкой по пользователю. Счётчик и время блокировки хранятся в users; проверка пароля и изменение счётчика сериализуются блокировкой строки PostgreSQL, в том числе между экземплярами RMS. Пятая ошибка уже возвращает блокировку. Во время блокировки верный PIN также отклоняется; новые попытки не продлевают срок. Успешный вход или истечение блокировки сбрасывают счётчик. Для обычных пользователей при создании допускается пятизначный цифровой PIN; для администраторов сохраняется минимум 8 байт.

Ответ блокировки: HTTP 401, `{"resultCode":1001,"result_code":1001,"messages":["Пользователь заблокирован до 2026-09-14T03:15:00Z"],"blockedUntil":"2026-09-14T03:15:00Z"}`. `resultCode` сохранён для совместимости с остальным API; `result_code` — его алиас в ответе блокировки. Код 1002 означает ошибку Origin/CSRF (403), 1003 — недействительную сессию (401).

Интеграционные тесты `auth_integration_test.go` проверяют конкурентные PIN, сохранение блокировки между сервисами, сброс после истечения, одноразовый refresh и откат неуспешной ротации. Используйте только тестовую БД в `TEST_POSTGRES_DSN`.
